# RGH3 (glitch2m) image build model

Worked out from real xeBuild 1.21 output for a 16 MB Trinity: two J-Runner
builds, a NAND read-back and that console's CPU key (none of which are in this
repository). The per-console part and the ECC are re-checked by
`tools/test_build_image.c` against your own files; the bootloader-chain notes
further down come from `tools/rgh3_reference_builder.py`.

## Headline result

**The bootloader + kernel chain is console-INDEPENDENT.** A "glitch2 mfg"
(glitch2m) image, which is what RGH3 uses, does not tie CB_B/CD to the CPU key:
their keys come from per-build nonces stored in the image. One image boots on
any console of the same model.

What IS per-console (found by diffing two J-Runner builds and a NAND read-back
of one Trinity, with its CPU key — `tools/test_build_image.c` re-checks all of
it against your own files):

| what | where (logical) | how it is bound to the console |
|---|---|---|
| KeyVault | 0x4000..0x8000 | `HMAC16 + RC4`, keyed by the CPU key (format below) |
| config blocks | 0xF70000..0xF80000 | plain data: SMC config (fan/thermal calibration) at 0xF7C000, settings at 0xF78000 |
| `secdata.bin` | flash filesystem | same format as the KeyVault, no HMAC suffix |
| `extended.bin` | flash filesystem | same format as the KeyVault |
| `crl.bin`, `dae.bin` | flash filesystem | first 0x120 bytes fixed, body differs per build — format NOT worked out |
| `fcrt.bin` | flash filesystem | per-console, format not worked out |
| mobile blocks | FsBlockType 0x31..0x3F | dashboard caches written by the console |

Everything else — header, SMC program, CB_A/CB_X/CB_B/CD/CE, CF/CG, patches,
dashboard files, the filesystem directory — is identical for every console
built with the same xeBuild options.

The earlier version of this document said the SMC config was merged into the
SMC region at 0x1000. That was wrong: the SMC region is the (universal) glitch
SMC program; the per-console SMC config is a separate block at 0xF7C000.

### KeyVault-style encryption (KeyVault, extended.bin, secdata.bin)

```
plain[0x10..0x18)  8 random bytes
hdr  = HMAC_SHA1(cpukey, plain[0x10..] + suffix)[:16]     suffix = 07 12 (KV, extended.bin), empty (secdata.bin)
key  = HMAC_SHA1(cpukey, hdr)[:16]
file = hdr + RC4(key, plain[0x10..])
```

xeBuild re-encrypts the KeyVault with new random bytes on every build, so two
images of one console have different KeyVault bytes but identical plaintext
from 0x18 on. A blank `extended.bin` (8 random bytes + zeros) regenerated by
this firmware with the same random bytes is byte-identical to xeBuild's.

### NAND spare / ECC

Small-block spare (16 bytes): FsSequence0, BlockID lo, BlockID hi, FsSequence1,
FsSequence2, BadBlock (0xFF = good), FsSequence3, FsSize, FsPageCount, 2 unused,
then a 32-bit little-endian word whose **low 6 bits are FsBlockType** (0x30 =
filesystem root, 0x31.. = mobile data) and whose upper 26 bits are the ECC.
The 6 type bits are an input to the ECC. `main/nand_ecc.c` reproduces all 32768
stored ECC words of real images.

## Builder (what the firmware does)

```
in : dump  (16MB raw, the target console)
     base  (16MB raw, a finished RGH3 image for the same model + patch set)
     cpukey of the target (optional)
out: flashable RGH3 image (16MB raw)

refuse if the dump's KeyVault/config blocks are bad or remapped
if cpukey: refuse unless the dump's KeyVault HMAC verifies
same_console = base KeyVault verifies with cpukey (no key: KeyVault bytes equal)

for each raw page:
    KeyVault, config blocks      -> dump page (ECC refreshed)
    blocks of the 5 files        -> dump's copy of the file, read through the
                                    dump's own filesystem; else a fresh blank
                                    (secdata/extended, needs cpukey); else base
    mobile blocks                -> base if same_console, else erased
    everything else              -> base page, untouched (spare included)

self-check: every page's ECC, KeyVault == dump, filesystem opens,
            secdata/extended verify with cpukey
```

Feeding a J-Runner image as both dump and base reproduces it byte for byte.

**Not confirmed on hardware:** booting an image re-targeted at a *second*
console. In particular a console whose dump has no `crl.bin`/`dae.bin`/
`fcrt.bin` gets the base's copies, which it cannot decrypt.

## Bootloader chain layout (unECC'd / logical)

```
@0x8000  CB_A 10918  size 0x1AF0   encrypted (1BL chain) — RGH3 injection blob, copied verbatim
@0x9AF0  CB_X 15432  size 0x0400   encrypted            — RGH3 exploit shim, copied verbatim
@0x9EF0  CB_B 9188   size 0x7800   PLAINTEXT + patches  — see below
@0x116F0 CD   9452    size 0x52B0   encrypted (build key) — see below
@0x169A0 CE   1888    size 0x5606A  encrypted (HV+kernel) — universal, copied verbatim
@0x13C000 first XEX2 (flashfs/dashboard) — universal
```

ECC note: unECC = strip the 0x10 spare from each 0x210 raw page → 0x200 logical.
Chain walk: header[0x8:0xC] = first loader offset (BE); each loader
name[0:2], ver[2:4] (BE u16), size[0xC:0x10] (BE u32).

## CB_B 9188 — PLAINTEXT, not encrypted  ✅ byte-exact

```
CB_B = cbb_9188.bin (stock plaintext, contains "XBOX_ROM")
     + patches_g2mtrinity.bin section 0   (byte-addressed, u32 count, data)
     + build nonce copied into [0x10:0x20]
     (hash field [0x20:0x40] as emitted by xeBuild; zero in donor's [0x30:0x40])
```
No RC4. The glitch chain reads CB_B as plaintext. The 16-byte value at
**CB_B[0x10:0x20] is the build nonce** that seeds the CD key (below).

## CD 9452 — encrypted with a BUILD key  ✅ byte-exact

```
plain = cd_9452.bin (stock) + patches_g2mtrinity.bin section 1
        (section 1 includes a 226-word extension @0x4F20 that grows CD)
pad    plain up to a 0x10 boundary
set    size field plain[0xC:0x10] = len(plain)   (BE u32)   -> 0x52B0
set    plain[0x10:0x20] = build CD nonce
key    = HMAC_SHA1( CB_B[0x10:0x20] , CD[0x10:0x20] )[:0x10]   # cbb_nonce is the secret
CD     = plain[:0x20] + RC4(key, plain[0x20:])
```
**The CD key seed is the CB_B nonce, NOT the CPU key** → console-independent.

## CE 1888 — HV + kernel, universal

Encrypted (ent ~8.0); `ce_1888.bin` is the stock plaintext (zeroed nonce). The
CE key is NOT an HMAC of any CD offset or the chain nonces (exhaustive
known-plaintext keystream search failed), and CE carries the compressed HV +
kernel which the §2 patches target at decompressed virtual offsets. CE is
**console-independent**, so the builder copies it verbatim from the universal
base rather than re-encrypting it. (Full on-device CE rebuild = future "trim
fat" phase; not needed for a working image.)

## Patch file format (`patches_g2mtrinity.bin`)

Sections separated by `0xFFFFFFFF`. Each patch: `u32 byte_offset, u32 word_count,
word_count*4 bytes data` (big-endian). Mapping for g2m:
- **section 0 → CB_B** (offsets within 0x7800)
- **section 1 → CD**   (offsets within CD; includes the 0x4F20 extension)
- **section 2 → kernel/HV** (large virtual offsets into decompressed kernel)

Use `patches_g2mtrinity.bin` (glitch2-matrix) for RGH3 — NOT `patches_g2trinity.bin`
(plain glitch2) or `patches_trinity.bin`. The donor was built with g2m.

## Header fields

- magic `FF4F`, build 1888, first-loader offset at [0x8:0xC] (0x8000).
- KeyVault offset at [0x6C:0x70] (0x4000); SMC length/offset at [0x78:0x80]
  (0x3000 / 0x1000).
